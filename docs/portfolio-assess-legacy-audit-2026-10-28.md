# Portfolio & Assess: Phase 0 legacy audit

Date: 28 October 2026
Scope: repository audit and local database availability check; no SQL query ran and no schema migration was run.

## Findings

### Product surfaces

- `frontend/src/App.tsx` mounts the Personal Portfolio dashboard and workbench at `/portfolio` and `/portfolio/projects`, Assess at `/assess` and `/assess/interviews/:interviewId`, and public Portfolio profile/pack links at `/portfolio/u/:username` and `/portfolio/p/:token`. Legacy `/projects` and `/companies` workspace URLs redirect to their canonical surfaces; existing publication links at `/portfolio/:publicId` remain readable.
- `PremiumWorkspaceShell` labels the Personal-only product links **Portfolio** and **Assess**. `seo.ts` uses StudyCod Assess metadata for both canonical and compatibility company routes. The candidate invitation view is branded Assess. Frontend and backend interview modules now use Assess names; `/talent` API mounts remain as compatibility aliases. Historical migration names, schema/index/constraint names, and persisted queue/LiveKit identifiers remain unchanged to preserve database and active-session contracts.
- Frontend pages now follow the canonical product folders: Portfolio workbench, publication, and review pages are under `frontend/src/pages/portfolio`; company assessment and interview pages are under `frontend/src/pages/assess`. Assess uses the shared Assess workspace shell/style layer. API clients live in `frontend/src/lib/api/portfolioProjects.ts`, `portfolio.ts`, `assessCompanies.ts`, and `assessInterviews.ts`.

### Backend and persistence

- Canonical API mounts are `/portfolio/projects`, `/assess/companies`, and `/assess`, plus the unauthenticated `/api/portfolio-public` profile/share API. Compatibility mounts remain at `/projects`, `/api/projects`, `/project-companies`, `/api/project-companies`, `/talent`, and `/api/talent`; old published-project links are served through `/api/project-portfolio`.
- Portfolio project workspaces are a server-side raw-SQL subsystem in `routes/portfolioProjects.ts` and the shared `growthProjectQueue.ts`. It supports staged project drafts, immutable artifacts and versions, Judge jobs, timed checks, publications, review requests, and profile publication lookup.
- Assess company and interview flows are implemented in `routes/assessCompanies.ts`, `routes/assessInterviews.ts`, and the `assessInterview*` services. Company roles are `OWNER`, `HR`, and `ENGINEER`; candidate access is tied to the candidate's user ID. Interviews add LiveKit rooms, shared editing, consent, per-interviewer private notes, explicit feedback release, and code execution.
- Migrations `1792800000000`, `1792900000000`, and `1793000000000` create the `growth_project_*`, `growth_company_*`, and `growth_interview_*` tables. These tables are not TypeORM entities in `data-source.ts`; route/service code uses parameterized SQL directly. Their original `down()` methods would delete shared notifications, drop Portfolio and Assess tables, remove `notifications.related_path`, narrow shared notification enums, and delete interview-linked Judge jobs. The current notification model, routes, and UI still support those shared fields and types, and Assess still uses interview-linked Judge jobs. The `down()` methods now fail before issuing SQL and direct operators to an inventory-backed forward-only migration; focused tests verify no query runs. Any eventual cleanup still requires verified preservation and backup/restore evidence.
- The candidate technical task and interview execution reuse `growth_project_jobs`, `growth_project_artifacts`, the existing queue worker, and the existing Judge integration. No second Judge or editor exists.

### Existing work and data to preserve

- The current “legacy import” API is an explicit, user-initiated copy from completed Personal mini-project tasks (`tasks` with `MPJ:` subtitle), completed Personal course items with `projectSpec`, and Personal library attempts with `project_spec`. It copies code into an owned artifact and stores source kind, source ID, title, and description in `growth_projects.source_json`. It does not delete the source records.
- Growth-project publications are frozen to a selected version and can be revoked or rotated. Existing public links use `/portfolio/:publicId`; the route is already shared by those publication tokens.
- No standalone `Project` entity or general Portfolio profile/evidence-pack model was found. Existing portfolio pages present published growth-projects; evidence is currently limited to project versions, Judge checks, assessments, and reviews.
- `Organization` and `Membership` are the EDU tenancy model. Hiring companies use separate `growth_companies` and `growth_company_members` tables. Company membership is not EDU membership, and the route helpers require a Personal user without changing global roles, plans, subscriptions, or EDU permissions.
- Learning mini-projects and `projectSpec` fields are used by Personal course learning and EDU lessons/tasks. These are learning content and execution contracts, not the old Project product; they must remain intact.
- Historical Personal Judge grades cannot be safely backfilled as verified Portfolio evidence. The old submit path stored the per-test summary in `grades.ai_feedback` display text, but no structured verifier, verdict, or test counts; other grade paths also write that field, including model-generated feedback. The migration therefore leaves those provenance columns null on old grades. Personal task history remains available, but only submissions with server-persisted Judge facts can be auto-cited as verified evidence.
- Repository inspection cannot establish production row counts, the number of active public links, or backups. The configured application loopback database target was rechecked on 28 October 2026 and refused TCP connections before any SQL was executed. At that preflight, no Docker or MySQL/MariaDB command or matching Windows service was available, and `DB_CONTRACT_DATABASE_URL` was not configured. A separate disposable MySQL runtime was later prepared for the synthetic contract only. Neither check says anything about production inventory or backup state. Backend test startup loaded local dotenv configuration in test mode; no values were printed.

### Current safeguards and test coverage

- Project and company writes use authenticated Personal-user checks. Company data requires active membership and company-scoped roles. Candidate code is only exposed after candidate submission; withdrawn cases omit code. Interview code waits for candidate consent, each interviewer reads only their own private note, feedback is candidate-visible only after explicit release, and the old project-job endpoint cannot retrieve interview executions.
- Successful company assessment-list and dossier reads, plus company-staff interview-detail reads, append `assess.company-assessments.list.read` or `assess.candidate-result.read` events to the existing audit log after tenant/role checks. Events identify the actor and candidate assessment and include scope, role, and status/count metadata; they omit answers, reviewer notes, source code, filenames, Judge output, and candidate names. Denied membership reads emit no event. High-frequency live interview state polling is not logged as separate user reads.
- Focused tests cover company dossier privacy and withdrawal, interview consent/role/editor protections, immutable quiz answers, reuse of the durable Judge queue, freezing final candidate code, HR interview-kit creation, the technical-task route's HR denial, company-scoped assessment lookup, selected-version pinning, public/hidden test separation, reviewer-controlled public evidence grants, and rejection of caller-supplied code. Added coverage for Skill Evidence and Evidence Packs is summarized in the current-slice verification below.

## Recommended implementation sequence

1. Add a first-class Portfolio profile and user-authored work through additive schema/API changes. Keep existing publication URLs working and compose existing published project versions into the profile only with explicit owner selection.
2. Add a versioned skill taxonomy and server-derived evidence references. Never accept client-supplied verdicts or ownership; validate every source against the authenticated owner and source permissions. Keep code private unless the owner explicitly publishes it.
3. Add Evidence Packs with scoped opaque share grants, expiry, revocation, and a public viewer that returns only selected material. A distinct route such as `/portfolio/u/:username` avoids colliding with existing `/portfolio/:publicId` links.
4. Evolve the existing company assessment workspace into StudyCod Assess by reusing its tenant boundaries, Judge queue, and interview workflow. Do not merge hiring companies into EDU organizations or make Portfolio a prerequisite for normal EDU use.
5. Remove old menu labels/routes only after equivalent Portfolio/Assess paths exist. Preserve or deliberately redirect each public URL, retain user data, and do not drop `growth_*` tables without a verified export/migration, backup, and separate production approval.

## Implementation status through the first reviewable product slice

The following changes are implemented in the working tree; they are not deployed and their migrations have not been run against a live database.

- Portfolio now has an additive profile/work schema and authenticated Personal-only APIs. Users choose a display name rather than inheriting their account name, choose profile/work visibility, curate a profile-level technology list, and can explicitly opt into showing their account photo. Photo sharing defaults off and applies only to a public profile or a pack whose owner selected profile sharing. Users can also explicitly add their existing published StudyCod work. The old `/portfolio/:publicId` publication route remains intact. The dashboard links to `/portfolio/projects` so private/in-progress work remains reachable inside the Portfolio workspace.
- Skill Evidence is limited to the user's own Personal `CODE` task grade with persisted `verification_method=ONLINE_JUDGE`, `judge_verdict=AC`, and `tests_passed=tests_total>0`. AI/Web grades are explicitly marked as other verification methods and cannot qualify. Public cards return only the owner-authored description and skill tags plus task title, language, Judge verdict, test counts, and date; they never return a code snapshot or hidden tests. Skill tags describe the selected submission, not overall proficiency.
- Personal Judge grades persist a verdict that agrees with the submit route's effective per-test result. A full pass records `AC` even for the legacy no-input free-output fallback where the worker can report `WA`; partial or malformed test counts cannot be promoted as accepted evidence. Three focused verdict-resolution tests and the backend typecheck passed.
- Skill Evidence also supports completed Personal course activities and global courses, active public StudyCod project publications, completed interviews whose reviewer explicitly allows a public Portfolio citation, reviewed Assess Judge tasks whose technical reviewer explicitly permits a public summary, and completed public contests after their safety-adjusted official scoreboard release. The evidence row snapshots its source metadata and revalidates that source before public or pack reads; company reviewers can revoke the two Assess sharing grants. These sources exclude EDU records, unreleased/private interview notes, hidden/private contest results, and source code.
- Evidence Packs use 32-byte random bearer tokens. Only SHA-256 hashes are stored; raw tokens are returned once at creation. Each grant stores explicit work/evidence IDs, optional profile sharing, and an expiry of 1–30 days. Each read checks revocation and expiry and returns only selected active items. The owner can revoke active links. Archived material disappears from the pack. Because these are bearer links, anyone who receives an active URL can view the selected items, including items marked private in the public Portfolio; the creation UI states this.
- Existing StudyCod project creation/versioning now lives at `/portfolio/projects` as the Portfolio workbench and uses the canonical `/api/portfolio/projects` API. Old `/projects` browser URLs redirect there with their query string preserved; `/api/projects` remains mounted for existing clients and links. The workbench remains because it stores version history and its Judge-checked versions are used by Assess. Company Assess can still choose only candidate-consented project versions. `/portfolio/:publicId` publication links are unchanged.
- StudyCod Assess now has a canonical `/assess` route and `/api/assess` API clients. The old `/companies` and interview URLs redirect to `/assess` equivalents; old backend `/project-companies` and `/talent` mounts remain as compatibility aliases for existing notifications and links. Company membership, candidate consent, EDU organizations, subscription checks, and the Judge queue were not changed.
- Newly issued project-review, company-assessment, candidate-task, interview, and calendar-invitation links now use `/portfolio/projects` or `/assess` canonical browser routes. Generated interview calendar invitations identify the product as StudyCod Assess. Existing notifications and calendar events keep their saved legacy targets, which continue to resolve through the compatibility redirects.
- The shared shell used by the company workspace and interview room is now named `AssessWorkspaceShell`; its live component/style dependencies were verified before renaming. Both routes still use the same shared chrome and CSS classes.
- Evidence Packs can have a specialization label, selected work/evidence, optional profile details, an expiry of 1–30 days, and revocation. Sharing profile details is opt-in by default.
- The versioned starter taxonomy contains 41 owner-selectable skills across Java, all 19 Judge-supported language families, algorithms/data structures, Backend, and engineering practices. Portfolio work stores up to 12 validated tags; Skill Evidence stores up to 8. Public work and Evidence Pack views show only the tags the owner selected. Labels explicitly say these tags describe an item and do not certify proficiency.
- Evidence Pack creation can suggest work and evidence using exact matches between the specialization and item metadata (title, description, role, technologies, or skill labels/categories). Suggestions are visibly marked but never selected automatically; the owner chooses every shared item.
- Twelve additive migrations create Portfolio profiles/works, store Personal submission verification facts, create Judge Skill Evidence and Evidence Packs, add validated skill tags to Portfolio work, add source-linked Skill Evidence, add profile technologies and opt-in photo sharing, persist owner-selected order across both evidence sources, store the private Personal birth year required for age-gated sharing, index server-enforced Assess interview expiry, and add Evidence Pack competency selections. Their `down()` methods refuse to drop configured feature data or saved ordering/selections. No migration was run, no production database was queried, no deployment was performed, and no existing `growth_*`, learning, or EDU row was copied/deleted.
- Portfolio owners can reorder Judge-backed and source-linked Skill Evidence together. The saved order is used on public profiles and Evidence Pack views; the endpoint validates the complete active owner-owned list in a transaction. Migration `1794000000000` adds the order columns and indexes and refuses rollback after an owner changes the order.

The `growth_*` subsystem remains the system of record for in-progress project versions and hiring assessments. Only published growth-project versions can currently be added as Portfolio work; the full in-progress project builder and its prior-work importer now sit inside the Portfolio workbench. A complete historical row migration is intentionally deferred until a read-only inventory, backup evidence, item mapping, and production migration review exist. Existing rows remain in place and reachable.

### Inventory and data-change gates

1. Confirm the intended database identity and schema with the database operator before opening a connection. Use a read-only database account; do not pass credentials in shell history, report output, or this repository.
2. Record the approved backup identifier and a successful restore-test reference outside the SQL result. An unverified snapshot or backup age alone does not satisfy this gate.
3. Run `portfolio-assess-data-inventory-readonly.sql` with a SQL client configured to stop on the first statement error. Confirm the returned legacy tables, `grades` verification columns, and `portfolio_evidence_packs.skill_ids_json` before interpreting aggregate counts. The script intentionally fails when its required legacy schema is absent.
4. Run `portfolio-assess-portfolio-data-inventory-readonly.sql` only when the first report confirms all five Portfolio tables, all four verification columns, and the Evidence Pack competency column. If the schema is partial, stop and report the missing migration state instead of retrying statements against missing tables.
5. Store the timestamped aggregate output with the backup reference in the approved restricted location. Review active publications, in-progress versions/jobs/interviews, notifications, and the broad Personal Learn source-candidate counts against the mapping above. Candidate counts are not importability counts and never authorize source deletion.
6. Before proposing any row migration, restore the backup into an isolated clone and dry-run an idempotent mapping. Verify owner/source identity, selected immutable version, count reconciliation, preserved legacy URLs, unchanged source rows, and that private code/tokens never appear in public output. Document a record disposition for anything not mapped.
7. Destructive cleanup requires a separate migration review after that dry run. Keep legacy storage and compatibility routes until all mapped data has a working destination and the restore procedure has been exercised. This goal does not authorize production DDL or deployment.
